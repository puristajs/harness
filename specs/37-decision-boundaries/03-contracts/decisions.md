# Normative decision contracts

All requirements below are approved D2 decisions executed mechanically by tickets. The exact public symbols are inventoried here; symbols not identified as public remain private. Optional properties are omitted, not null. All closed objects reject unknown properties at runtime; callback functions and AbortSignal references are not serialized. `JsonValue` is the sole open JSON leaf and requires finite numbers, acyclic arrays/plain objects, string keys, and no undefined, function, symbol, bigint, or custom prototype. Raw ingress may be `unknown` only inside a parser, never in an exported closed result.

## CTR-DB-EVIDENCE — safe evidence and schema ownership

Create `packages/harness/src/decisions/{schemas,types,evidence,identity,execution,index}.ts`. Put runtime Zod schemas for non-generic closed records in `schemas.ts`; infer their TypeScript aliases using `z.output`, rather than repeat interfaces. Generic correlated callback/phase types live in `types.ts`. Reuse the existing canonical `JsonValue` and export `isJsonValue` from `models/json.ts`; replace the private duplicate implementations in tools/mcp/schema.ts, tools/mcp/runner.ts and testing/replay.ts with this function. harness/types.ts must re-export the canonical JsonValue rather than repeat its union. The JSON validator rejects cycles without stack overflow and does not stringify candidate values into errors.

Public `DecisionSource` is `{kind,id,version?,ruleId?}`. `kind` is `permission|policy|exposure|interceptor|guardrail`. IDs/version/rule IDs are application configuration references: nonempty strings of at most 128 Unicode code points, with no control characters. Do not derive them from inspected content. Preserve configured rail names containing spaces. Public `DecisionEvidence` is `{decisionId,source,phase,reasonCode?}`; `phase` is `input|before_model|after_model|output|tool_input|permission|policy|approval|tool_output|exposure|retrieval`. `decisionId` is runtime-owned. `reasonCode` is optional deployment-defined ASCII `/^[a-z][a-z0-9_]{0,63}$/`; reject malformed codes, never sanitize prose into codes. Values matching this syntax are still subject to the application prohibition on content-derived values.

Callbacks return only their result plus optional `reasonCode`; they cannot supply evidence IDs, source IDs, approver identity, arbitrary metadata, prose, tags, or severity. An external policy adapter may additionally return `ruleId` (same bounded identifier), because it owns its internal rule reference. The runtime constructs evidence after validation. Reason-code registration is not required; no new catalog API is introduced.

Operational events and errors use one exact projection of evidence and occurrence references. Raw evaluation inputs, invocation metadata, approval subject, reviewer identity/comments, matched text, and provider continuation are never copied into it. Application-owned review persistence may hold these values under application authorization/retention; core audit sinks do not receive them.

Public `DecisionBlockedError` (`DECISION_BLOCKED`, category `interceptor`, non-retriable) carries `{evidence}` and the fixed message `Decision blocked execution.` It is used by explicit interceptor and guardrail blocks, including retrieval. Public `DecisionEvaluationError` (`DECISION_EVALUATION_ERROR`, category `interceptor`, non-retriable) carries `{evidence,failureKind}`; `failureKind` is `invalid_result|callback_failed|callback_timeout|invalid_transform|invalid_continuation|audit_failed|sensitive_data_detector_failed|sensitive_data_invalid_result|sensitive_data_codec_failed`. Its message is fixed: `Decision evaluation failed closed.` Preserve causes internally, never in serialized errors. Delete `AgentInterceptorError`, `PolicyEvaluationError`, `GuardrailBlockedError`, and `GuardrailEvaluationError` classes and exports after consumers move; do not add aliases. Keep `GuardrailsConfigError`, `PermissionDeniedError`, `PolicyDeniedError`, `OperationCancelledError`, `OperationTimeoutError`, and `ValidationError` for their distinct meanings. Explicit permission/policy denial remains a recoverable model-visible tool result with a fixed message and safe evidence. Both new decision errors are terminal for the agent invocation and never serialized as a recoverable tool result.

The recoverable denial constructors use the same evidence projection: `PermissionDeniedError(evidence, cause?)` has fixed message `Permission denied.` and exact metadata `{evidence}`; `PolicyDeniedError(evidence, reason, cause?)` has fixed message `Tool call denied by governance policy.` and exact metadata `{evidence,reason}`, where reason is exactly `policy_deny|approval_rejected|approval_unavailable`. Constructors validate evidence and reason before serialization and omit causes. Permission denial uses permission-phase evidence, policy denial or unavailable approval uses its policy demand evidence, and an approval rejection uses approval-phase evidence derived from the first ordered demand. Do not repeat tool/agent/policy/rule identifiers or an effect alongside evidence; run/tool event envelopes carry occurrence references. These constructors accept no message or arbitrary metadata argument.

## CTR-DB-LIFECYCLE — one bounded callback executor

Public `DecisionExecutionContext` is `{signal: AbortSignal, deadline: number}` where deadline is epoch milliseconds. Public `runDecisionOperation<T>(context, operation)` invokes `operation(signal)` at most once and resolves its value, throws the normalized parent cancellation/timeout, or throws the existing `OperationTimeoutError` with scope `decision` on its own elapsed deadline. Add `decision` to that error's scope union; do not add a timer-specific error class. The owning decision boundary converts a decision-scoped timeout into `DecisionEvaluationError(callback_timeout)`. No invocation occurs if the signal is already aborted or deadline has passed. Deadline must be finite; invalid configuration rejects at build/compile time. The helper relays abort to a child controller, races non-cooperative callbacks, suppresses late resolution/rejection from continuation, and clears its timers and listeners on every exit. No callback retries occur in this helper.

Core and addon must use this one helper for interceptors, native predicates, exposure predicates, external policies, approval, audit, and rail actions. Remove `evaluateAction`'s private timer/abort implementation. Replace decision-path uses of `withToolSignal`; keep unrelated model/sandbox timing outside this refactor. Existing `runtime/abort.ts` remains the canonical cancellation error classifier and is reused internally by the helper, not copied.

Add `defaults.decisionTimeoutMs` with default 10_000, positive safe integer. Each decision callback has its own deadline `now + decisionTimeoutMs`; the callback context reports the minimum of this and enclosing tool/run deadlines. The executor uses the owning callback deadline separately from the enclosing parent signal, so enclosing timeouts retain their identity. Guardrail `actionTimeoutMs` and action `timeoutMs` remain, default 10_000, and can only shorten the enclosing decision deadline. This intentionally replaces independent repeated full tool budgets.

The tool deadline starts when its preflight begins and covers input rails, input parsing, permissions, governance, approval, handler, and output rails. It is `start + defaults.toolTimeoutMs`. A zero tool timeout retains the existing disabled-tool-deadline setting; decision callbacks remain bounded by 10_000 or their configured shorter value. Time queued before preflight does not consume this budget. The tool lifecycle owns a linked AbortController created at preflight start, linked to run/batch cancellation, with one timer aborting with `OperationTimeoutError(scope:tool)`. It owns cleanup through batch completion. Handler execution uses a private tool-operation race against this controller, never a fresh tool timer or decision executor. No handler is called after abort; late success/failure is consumed without emitting output. Tool timeout zero creates no tool timer. Decision boundaries call the shared executor with this parent signal and their own callback deadline; public callback context exposes the effective minimum. The executor checks parent signal before own deadline both at entry and timer settlement; already observed parent cancellation wins, otherwise first observed settlement wins. Tool timer is installed before child decision timers, so equal tool/decision deadlines produce tool timeout. Run cancellation propagates as its original normalized reason. Caller cancellation remains `OperationCancelledError`; an enclosing run/tool timeout remains `OperationTimeoutError`. A callback's own timeout is a terminal decision-evaluation failure. No late approval can execute a tool.

Interceptors receive the actual step, selected model, and effective parsed agent input, not constant step zero or the original invocation input. Decision contexts carry these values transiently; evidence projections do not.

## CTR-DB-GOVERNANCE — one immediate approval path

Retain `.governance(...)`, its late builder position, native/rule/adapter/exposureRule helpers, default deny for unmatched execution policies, and effect precedence `deny > require_approval > audit > allow`. `shadow` evaluates/records governance decisions without hiding, denying, or requesting approval for governance effects. Coarse agent permissions remain enforced even in shadow mode. Exposure-only or approval-only configuration never applies execution defaultEffect when no execution policies exist.

Replace `PermissionMode` with `allow|require_approval|deny`; remove `ask`, `onPermission`, `OnPermission`, `PermissionContext`, and `PermissionDecision`. Preserve existing bash/write/edit allow/deny pattern semantics and default allow. Read-only built-ins remain subject to allowlisting/exposure/governance but cannot be denied through `AgentPermissions`. A permission `require_approval` is collected with governance approval demands, not executed as a separate callback. Any effective permission/policy deny prevents approval. Exactly one approval request covers all remaining approval demands for a tool occurrence. Permission-derived evidence uses source `{kind:'permission',id:canonicalToolId}`.

`GovernanceContext<S,K>` is a distributive union over `K`, preserving correlation between `toolId` and parsed `input`; native stored rules support one or multiple selected tools without forcing a union of singleton definitions. Omitted `tools` means all configured and built-in tool IDs, with that correlated input union. Built-in/MCP parsed input remains validated JsonValue. Context contains `{toolId,input,callId,invocationId,agentId,runId,sessionId,workflowId?,step,metadata,signal,deadline}`. Metadata is the existing explicitly open JSON application context and is never operational evidence. Schema normalization runs once per tool call before these contexts are constructed; the exact parsed value is shared read-only with approval and handler.

`GovernanceDecision` contains `{effect,reasonCode?,ruleId?}`. Native rule definitions additionally retain `id,description?,tools?,when?`; effect and reasonCode are static configuration. Remove GovernanceRiskLevel and GovernanceAuditContext exports; GovernanceAuditRecord is their only audit-record replacement and no alias remains. Remove decision/rule `message`, `reason`, `metadata`, `tags`, `riskLevel`, `decisionId`, `policyId`, and `policyVersion` result fields; policy identity/version come only from registered policy configuration. External evaluator returns one decision, an ordered readonly decision array, or `undefined` to abstain. Only actual `undefined` abstains; null, false, malformed arrays, unknown effects, and extra fields fail closed. Native predicate returns exactly boolean. Configuration validation applies the same closed enums and known tool checks as runtime results.

`GovernanceApprovalRequest<S>` contains `{approvalId,subject,demands}`. Subject is the correlated transient tool subject `{toolId,input,callId,invocationId,agentId,runId,sessionId,workflowId?,step}`; input is parsed effective input. Demands are readonly `DecisionEvidence[]`. `GovernanceApprovalResult` is exactly `{decision:'approved'|'rejected',reasonCode?}`. `GovernanceApprovalProvider<S>.request(request, execution: DecisionExecutionContext)` returns a Promise of that result. No request/input is included in run events. Applications authenticate reviewers and persist comments/identities outside this callback result. An approval is for this occurrence and input only: no session grant, cross-call cache, retry, or authorization escalation.

Governance configuration may contain policies, exposure rules, or an approval provider alone. `enabled:false` disables policy/exposure evaluation only; its approval provider remains available for enforced permissions. Omitted governance with a static permission approval requirement is a build error. An approval-only configuration is valid and does not activate execution default deny. At build time, statically configured permission/native-policy approval requirements in enforce mode require a provider; reject otherwise with `HarnessConfigError`. A dynamic external-adapter approval demand without a provider produces a safe recoverable `PolicyDeniedError` with `approval_unavailable`. Permission demands remain provider-required even when governance is shadow. A rejected permission-only approval maps to `PermissionDeniedError`; rejection involving an enforced governance demand maps to `PolicyDeniedError`. Unexpected approval output throws terminal `DecisionEvaluationError(invalid_result)`.

`GovernanceAuditSink.record(record, execution)` receives a public `GovernanceAuditRecord` containing only `{evidence,toolId,callId,invocationId,agentId,runId,sessionId,workflowId?,step,effect,enforced}`; no input or metadata. Audit invocation is ordered after decision validation and before the effect; failure/own timeout fails closed with `audit_failed`. It is invoked in shadow mode too. Record matched decisions in declaration order; mark `enforced` true only for decisions actually contributing to the enforced restriction. An approval demand suppressed by a deny is not marked enforced. Effects are reduced with a linear scan, not sorted copies. No new audit transport or persistence service is introduced.

## CTR-DB-IDENTITY — occurrence identity and events

Public `DecisionOccurrence` is `{invocationId,step,runId?,agentId?,sessionId?,workflowId?,toolId?,callId?}`. Step is a nonnegative safe integer; occurrence reference strings use the wait-ID rule (1..200 ASCII characters), rather than the 128-character source-configuration limit. Invocation-bound evaluation supplies existing run/agent/session references; standalone retrieval defaults step to zero and absent references remain omitted in evidence, encoded as null in identity. Retrieval accepts optional caller `invocationId` validated by that occurrence rule. Create one internal identity function: SHA-256 over UTF-8 JSON encoding of the ordered tuple `[runIdOrNull,invocationId,phase,step,toolIdOrNull,callIdOrNull,source.kind,source.id,source.versionOrNull,source.ruleIdOrNull,ordinal]`; return `decision_` plus lowercase hex. No truncation or character replacement. `invocationId` is the existing delegationCallId for child agents; for direct agents it is the runId. Each standalone retrieval execution generates one ULID invocation ID with the existing core ULID helper when none is supplied; separate retrieval calls do not share it. Ordinal is zero-based evaluated outcome position within that phase/subject in configured order. Each invoked native rule, exposure rule, permission boundary, interceptor, or rail action reserves one ordinal even when it abstains. An external policy reserves max(1, returned array length) positions; an empty array or undefined reserves one. Skipped callbacks reserve none. External array elements use consecutive positions; callback failure uses its first reserved position. Execution concurrency must not assign ordinals by completion order. Exposure identity therefore includes toolId. Approval ID is `approval_` plus SHA-256 of UTF-8 JSON tuple `[runId,invocationId,"approval",step,toolId,callId,orderedDemandDecisionIds]`. IDs correlate one invocation; they are not approval tokens or an independent exactly-once guarantee.

Retain event names `policy.evaluated`, `policy.exposure`, `approval.requested`, and `approval.finished`, replacing payloads in one clean cut. Common occurrence fields are `{runId,agentId,invocationId,toolId,step,callId?}`; callId is required except exposure. Policy/exposure events add `{evidence,effect,enforced}` with their respective effect enums. Approval requested adds `{approvalId,demands}`. Approval finished adds `{approvalId,outcome,reasonCode?,errorCode?}`; outcome is `approved|rejected|cancelled|timed_out|failed`, errorCode is present only on failed/timed_out/cancelled and is a fixed Harness code. No subject, approverId, prose, or metadata. Existing event transport envelope timestamps and session binding remain unchanged.

Once requested emission resolves, attempt exactly one terminal emission on every callback exit. If terminal emission fails, preserve the original cancellation/failure; after a successful approval, event delivery failure terminates before tool execution. Do not retry event delivery here. This is a runtime attempt guarantee, not guaranteed durable delivery through a failing storage adapter. Existing storage/event transport retains responsibility for persistence and idempotency.

## CTR-DB-TOOLS — prepared input and output

Move tool lifecycle code into `agents/tool-execution.ts`; leave `agents/index.ts` responsible for loop orchestration. Canonicalize tool names once and reject unknown/unexposed calls before rails. IDs, canonical names, ordering, and tool descriptors cannot be changed by interceptors. The private `PreparedToolInvocation` contains the existing canonical `ToolCallSpec` with transformed wire arguments, parsed input, tool binding, occurrence context, and deadline. Do not export a second public tool-call envelope.

For each provider batch, preflight tool-input interception and schema validation in call order before any tool handler or approval request starts. A terminal rail/validation-boundary failure aborts the batch without side effects. Ordinary schema ValidationError remains a recoverable per-call error and excludes that call from execution; terminal decision errors abort the batch. Then execute eligible calls using existing maxParallelToolCalls, with permissions → governance → single approval → handler → output validation → output rails. On a terminal error, abort the linked batch controller, stop admission, and settle/drain raced wrappers; handlers that ignore cancellation cannot be forcibly stopped. Already performed side effects are not rolled back; the application owns idempotency and uncertainty recovery. Recoverable permission/policy/tool errors remain ordered results and do not abort siblings.

Use transformed wire arguments in the model continuation and persisted assistant tool-call history. Use the once-parsed input in governance/approval/handler. These are intentionally distinct representations when schema normalization changes values; both are derived from the transformed proposal. Never persist original pre-rail arguments, even for denied or failed calls. For input-invalid calls, retain only the transformed wire arguments and safe validation error. Tool started events use the transformed wire arguments; persisted operational projection still redacts input. Do not alter a prepared input after policy/approval. Recursively freeze the JSON-compatible prepared arguments and parsed input before callbacks; callbacks must not mutate them. Non-JSON parsed tool input fails `ValidationError` before policy/approval.

Tool-output schema parses the handler output once. Output rails receive that validated JSON value. A transformed tool output must be JSON-compatible but is not reparsed through a potentially transforming handler schema; it is a deliberate model-visible presentation projection. TypeScript tool output remains the handler contract, while the interceptor projection is JsonValue. This distinction is documented and tested; no claim is made that a redacted model projection still matches the handler output schema.

Generic `beforeModel` transforms may replace messages only; tools, schema, generation call settings, and model identity are read-only and outside the transform result. Revalidate messages and recheck that tools are a subset of the exposed set before dispatch. Generic `afterModel` becomes allow/block only; response identity, tool calls, usage, and provider continuation cannot be transformed. This removes the path by which arbitrary hooks could replace authority-bearing envelopes or token accounting.

## Synthetic and approval evidence ownership

Order demands permission-first, then governance policy declaration order and each adapter result order. Approval evidence for approved/rejected and callback failure inherits the first demand source, uses the same tool occurrence with phase approval and ordinal zero; it is not a new configured policy. Requested events carry approvalId and demands; finished events carry only the declared terminal fields, without demands. Callback failure errors carry this approval-phase evidence. A permission-only demand therefore remains attributable to that built-in permission. Audit failure carries the evidence of the record whose write failed; it does not invent another audit source.

Unmatched execution default evidence uses `{kind:'policy',id:'governance.default',ruleId:'default'}`, ordinal equal to the next reserved position after evaluated policies; emit only when an execution-policy set exists and default deny applies. Exposure defaults use `{kind:'exposure',id:exposure.id ?? 'governance.exposure',version:exposure.version when present,ruleId:'default'}`; matched exposure rules replace ruleId with configured rule.id. Default exposure ordinal follows evaluated rules. Reserve these synthetic IDs against explicit policy IDs/rule IDs at configuration validation; native/external configured ruleId `default` is prohibited. Native policy source uses registered id/version and rule id; adapter failures before a result have registered id/version and no ruleId. Interceptor source uses its required configured interceptor.id; do not add an optional-ID fallback. Guardrail source uses configured rail id, with action.id as ruleId. Duplicate effective source IDs within one attached boundary reject configuration. No synthetic identifier incorporates inspected input.

## Native rule storage typing

Retain NativePolicyRuleForTool<S,K> as a strict configuration type with `when?: (ctx:GovernanceContext<S,K>) => boolean | Promise<boolean>`. No public predicate uses method bivariance. NativePolicyRule<S> is NativePolicyRuleForTool<S,GovernanceToolId<S>>, with a full correlated context union, not a mapped union of singleton rule objects.

The selector helper overload `rule<const K extends readonly GovernanceToolId<S>[]>(definition)` requires tools:K and types its predicate context as GovernanceContext<S,NoInfer<K[number]>>; infer selected tools from tools only, never from callback annotation. The omitted-tools overload accepts a strict full GovernanceContext<S> predicate. Both return NativePolicyRule<S>, normalizing a narrow configured predicate into a full-context callable using a private selector-membership type guard. This wrapper returns false outside its selected tools without invoking the original predicate; on a member it passes the same already-validated input through the narrowed context. Preserve id/description/effect/reasonCode/tools values. The generic type guard narrows only from validated toolId membership; it does not cast or reparse input. Runtime evaluator also uses the same selector-membership helper to skip nonmembers before invoking a rule or reserving its outcome ordinal. The shared helper avoids two independent matching implementations.

A raw rule passed directly to native must accept the full correlated union; developers use rule(...) for selector inference. Apply the same helper normalization to exposureRule and its input-free context. No exported bivariant shape, opaque registration brand, any/unknown predicate or double assertion is introduced. Negative type tests reject single-tool annotated callbacks without a selector, selector/callback mismatch, a narrow raw stored predicate and property access before discriminant narrowing. Positive tests accept mixed single/multi-tool helper rules in one native array. Runtime tests prove nonmember original predicates are never invoked.
