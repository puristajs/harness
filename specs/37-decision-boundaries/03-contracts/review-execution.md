# CTR-DB-REVIEW: application execution admission

## Boundary and records

Only the deterministic `examples/durable-human-review` application reference changes. HarnessStorage owns wait/signal/checkpoint state, never reviewer CRUD, payment authority or claims. Use injected application callbacks and fake providers; no production payment adapter or server is added. Infer records from local strict Zod schemas and reuse ExternalWaitOutcome.

`PaymentAction` is `{paymentId,amountCents,targetRevision}`. IDs are nonempty at most 200 characters under the wait-ID rule; amountCents is a positive safe integer; targetRevision is a nonnegative safe integer. `ReviewDescriptor` is `{businessKey,actionSchema:'payment-action-v1',definitionVersion:'payment-v1',targetRevision,executionDigest,expiresAt}`. SHA-256 lowercase hex digest is over UTF-8 JSON tuple `[paymentId,amountCents,targetRevision,'payment-action-v1','payment-v1']`. Deadline uses the core exact UTC millisecond timestamp rule. Business key is `payment:` plus paymentId; reject values exceeding the shared ID bound. Compute identityDigest as SHA-256 lowercase hex of UTF-8 JSON tuple `[businessKey,"payment-v1"]`. Session ID is `payment:` plus identityDigest; durable run/execution ID is `payment-review:` plus identityDigest; wait ID is `payment-wait:` plus identityDigest. These bounded opaque IDs satisfy existing durable-run and wait validators. Always derive the candidate waitId by this rule; do not interpolate raw paymentId into durable identities.

`ReviewTask` is `{businessKey,waitId,revision,action,descriptor,status,decisionEventId?,decidedBy?,approvedRevision?}`. Immutable action and descriptor are stored at creation. Status is `pending|approved|rejected|expired|cancelled`; delete consumed. Revision starts at 1; first terminal decision or automatic expiry increments once. ApprovedRevision exists only after approval and equals that resulting revision. Explicit decisions require decisionEventId and decidedBy; automatic expiry has neither. Pending has neither. No transition leaves a terminal review state.

`ExecutionReceipt` is `{executionId,receiptId}` with bounded IDs. `ExecutionRecord` is `{executionId,businessKey,approvedRevision,action,descriptor,status,receipt?}`. Action/descriptor are the immutable stored task values; status is claimed or succeeded, with receipt present exactly for succeeded. One businessKey binds one executionId. ExecutionId is the logical durable runId across retries, never an attempt ID. Return recursively frozen snapshots; callers cannot mutate stored state.

Public within this example only: `ReviewBindingError` extends HarnessError, code `REVIEW_BINDING_ERROR`, category `state`, non-retriable, fixed message `Review execution binding failed.` Safe details are `{reason}` with reason `missing_task|unauthorized|stale_action|execution_conflict|missing_claim|invalid_receipt|receipt_conflict|invalid_request|not_approved|expired|decision_conflict`. No action/principal/input in error details. Application store absence after Harness checkpoint replay is missing_task; do not reconstruct approval from wait state.

## Store and injected callback signatures

Methods are asynchronous and use strict records; all malformed arguments throw ReviewBindingError(invalid_request), except malformed receipts use invalid_receipt. Store operations are atomic within the reference store; this is not a production multi-process transaction implementation.

- `getOrCreate(input: {action:PaymentAction;waitId:string}): Promise<ReviewTask>`: look up businessKey first. Existing key requires identical action/schema/version and returns its original waitId/deadline without reading the clock or extending TTL. New key freezes action, computes descriptor and expiry from the injected clock plus positive safe-integer reviewTtlMs, and stores pending revision 1. Reject invalid/overflowing date arithmetic. A candidate retry waitId is ignored for an existing matching key; no second wait is registered.
- `get(businessKey:string): Promise<ReviewTask|undefined>`: return current snapshot, atomically auto-expiring pending tasks at now >= expiresAt. Approved decisions remain approved after deadline, but cannot admit a new claim. The store and example Harness in-memory adapter share the same injected clock `now:()=>Date`; default clock is defined only in application composition.
- `decide(input: {businessKey:string;expectedRevision:number;eventId:string;outcome:ExternalWaitOutcome;principalId:string;executionDigest:string}): Promise<ReviewTask>`: caller authenticates/authorizes the reviewer before this method. Compare digest to stored action; then apply clock expiry before CAS. Identical eventId/outcome/principalId/digest replay returns unchanged even when expectedRevision is the original revision. Any other terminal/different duplicate or stale expectedRevision throws decision_conflict. First valid decision increments revision once and captures approvedRevision for approved. Explicit expired is a normal terminal decision with event/principal. Store possession is not reviewer authorization.
- `readExecution(executionId:string): Promise<ExecutionRecord|undefined>`: return immutable claim or receipt state, without changing approval/expiry.
- `claimApprovedExecution(input:{businessKey:string;executionId:string;executionDigest:string;authorized:boolean;targetRevision:number}): Promise<ExecutionRecord>`: identical existing execution and task binding returns unchanged before new-admission checks. Different executionId for the key or changed digest is execution_conflict. For a new claim require authorized true, current task approved, now < expiresAt, matching digest, and targetRevision equal immutable action.targetRevision; fail respectively unauthorized, not_approved, expired, stale_action. Copy stored action/descriptor and approvedRevision atomically into claimed record. This freezes admission; later expiry/revocation does not revoke the claim.
- `recordExecutionReceipt(receipt:ExecutionReceipt): Promise<ExecutionRecord>`: require matching executionId claim or throw missing_claim; atomically set succeeded. Exact duplicate is unchanged; different receipt for the key is receipt_conflict. Workflow also checks returned executor receipt.executionId equals claimed executionId before recording, otherwise invalid_receipt.
- `readExecutionReceipt(executionId:string): Promise<ExecutionReceipt|undefined>`: derive from readExecution, not a second receipt store.
- `authorizeExecution(action:Readonly<PaymentAction>): Promise<boolean>` and `readTargetRevision(paymentId:string): Promise<number>` are required injected application callbacks. No hardcoded true in runnable usage. Values must be exact boolean/nonnegative safe integer; malformed values reject invalid_request. Rejection or unavailability before admission creates no claim/effect.
- `PaymentExecutor.execute(input:{action:Readonly<PaymentAction>;idempotencyKey:string}): Promise<ExecutionReceipt>`: the same key/action returns the same receipt with one logical effect. A different action for a used key rejects execution_conflict. The in-memory reference implements that map; uncertain real external outcomes require reconciliation of that same key or manual intervention outside Harness. No automatic retry or reconciliation service is introduced.

## Workflow ordering and replay

Task creation stays in its existing idempotent workflow step. **Before entering the execution step on every invocation, including checkpoint replay**, call get(businessKey), require the task exists, and compare current invocation action and version/digest with stored immutable action. Changed input is stale_action even if a receipt or execution checkpoint already exists. This read is deliberately outside the replay-skipped step. Resume existing external wait using stored task waitId/deadline; a wait approval alone grants no authority.

Inside `ctx.step('execute-payment-v1', ...)`, readExecution(runId) first. Require an existing record's businessKey/action/descriptor/digest to match the bound task. If succeeded return stored `{receiptId}`. If claimed, skip new-admission authorization/revision checks and execute its immutable action with its stable key. If absent, run both admission callbacks, call claimApprovedExecution atomically, then use the returned record (including concurrent existing claim). Execute, require matching receipt identity, record receipt, return only `{receiptId}`. Executor rejection leaves claim intact. Expiry or callback failure/revocation after admission cannot prevent retry of that admitted action. Output is approved only after receipt/checkpoint success. No human callback keeps a Harness invocation alive; waiting remains existing suspension and replay.

## Acceptance windows

Cover creation before checkpoint, decision before signal, duplicate signal before resume, claim before executor, transient executor failure, effect success before receipt write, receipt before step checkpoint, checkpoint before final run commit, concurrent claims/resumes, changed input after receipt AND checkpoint, mismatched receipt executionId, missing application task after checkpoint, different executionId, new-claim expiry/rejection/cancellation/authorization denial, and expiry/revocation/current-revision callback outage after claim. For each assert one logical effect and one receipt with the original key, or explicit safe rejection before new effect. Inject checkpoint failures through the existing storage test seam. Never delete stored runs or disable retries to satisfy the tests.
