# Operations and acceptance

Implementation verification is local and hermetic: fake model providers, synthetic continuation fixtures, injected clocks, existing in-memory/SQLite storage and application executor fixtures. No model credentials, real payments, Docker requirement or new service. Missing local dependencies block the corresponding command; do not install or substitute an illustrative result. Record exit status and exact failing assertion, and distinguish preexisting failures with the preflight baseline. A red required gate cannot be accepted merely because it predates the ticket; record a blocker for the coordinator.

Before eventual deployment, drain old active runs under their matching old binaries. New binaries accept only the new source/API/event shapes. Existing data is retained; no automatic conversion/reset. Deployment/versioning/publication and destructive operations require a separate release authorization. A rollback uses the matching prior binaries and compatible drained environment, never converts new runs with an old reader. The implementation output includes a breaking-change inventory and gate evidence, not a migration guide.

DecisionEvaluationError terminates the invocation: operators inspect safe evidence ID/source/phase/failureKind and existing trace IDs. They never request raw prompt/matched text in logs. Approval cancellation/timeouts cannot execute tools later. A noncooperative external tool or missing payment receipt may require application reconciliation using the same execution identity; no automatic new payment key is permitted.
